# Minibar OS

Внутренний инструмент для работы с мини-барами отеля: учёт состояний и сроков, акцизы, GIH, списки, история операций и связанные рабочие процессы. Этот документ — техническая карта проекта для разработчиков и ИИ-агентов.

- **Репозиторий:** https://github.com/nicosare/minibar-os
- **Production:** https://tintink.ru/minibar-os/
- **Основная ветка разработки:** main
- **Клиент:** преимущественно desktop; отдельный мобильный клиент — VK Mini App.

> **Главное правило:** это рабочая система с реальными данными. Сначала изучай существующую реализацию и влияние изменений. Не экспериментируй с production-инфраструктурой и базой данных без отдельного согласованного плана.

## 1. Архитектура

~~~text
Desktop Web App ─────┐
VK Mini App ─────────┼──> Express REST API ───> PostgreSQL
VK Bot ──────────────┘           │
                                 └──> Live Events / SSE
Desktop Web App <──────────────────────┘

VK Mini App ──> VK API Proxy ──> VK API
~~~

Клиенты используют общий backend и PostgreSQL как основной источник данных. Клиенты не должны напрямую обращаться друг к другу или реализовывать независимую копию бизнес-логики. Для новых функций сохраняй единые правила в API/backend, если операция относится к общим данным или бизнес-процессам.

### Компоненты

| Каталог | Назначение |
|---|---|
| frontend/ | Desktop веб-интерфейс: HTML, CSS и JavaScript без отдельного frontend-фреймворка |
| backend/ | Express REST API, бизнес-логика и доступ к данным через Prisma |
| miniapp/ | Отдельный клиент VK Mini App |
| vk-proxy/ | Серверный прокси для разрешённых операций с VK API |
| vk-bot/ | VK Group Long Poll бот, передающий события в общий backend |
| docker-compose.yml | Описание production-сервисов и их связей |
| .github/workflows/desktop-smoke.yml | Desktop smoke-тесты и настроенный workflow деплоя |

## 2. Важные файлы

### Frontend

- frontend/index.html — точка входа, подключение CSS и JS-модулей.
- frontend/config.js — клиент API, заголовки запросов и базовый API URL.
- frontend/styles.css, frontend/design-system.css — стили приложения и общая дизайн-система.
- frontend/js/utils.js — общие утилиты.
- frontend/js/app-core.js — ядро приложения, базовый путь и маршрутизация вкладок.
- frontend/js/init.js — инициализация модулей для текущего маршрута.
- frontend/js/route-handlers.js — обработчики переходов и маршрутов.
- frontend/js/excise-module.js — работа с акцизами.
- frontend/js/deadlines-module.js — сроки и связанные операции.
- frontend/js/gih-module.js — GIH.
- frontend/js/history-module.js — история.
- frontend/js/calculator-module.js — калькулятор.
- frontend/js/inventory-module.js, frontend/js/lists-module.js — инвентаризация и списки.
- frontend/js/dashboard-module.js, frontend/js/settings-module.js — главная панель и настройки.
- frontend/js/live-sync.js — подписка на live-события и связь событий с доменами интерфейса.
- frontend/tests/desktop-smoke.cjs — браузерные smoke-тесты desktop-интерфейса.

Frontend — модульный vanilla JavaScript. Перед добавлением кода проверь, где уже находится соответствующая логика, как устроена инициализация и какие глобальные объекты использует приложение. Не создавай второй механизм маршрутизации, API-клиент или live-синхронизацию без необходимости.

### Backend

- backend/src/index.js, backend/src/app.js — запуск сервера и сборка Express-приложения.
- backend/src/init-db.js — инициализация/синхронизация схемы и связанные SQL-операции.
- backend/src/lib/prisma.js — клиент Prisma и перехват операций изменения данных.
- backend/src/lib/live-events.js — домены и публикация событий live-обновления.
- backend/src/lib/timezone.js — работа с часовыми поясами.
- backend/src/routes/ — HTTP-маршруты.
- backend/src/services/ — бизнес-логика, вынесенная в сервисы.
- backend/prisma/schema.prisma — исходная схема данных Prisma.

Перед изменением API найди маршрут, вызываемый сервис и используемые модели Prisma. Сохраняй существующие форматы ответов и ошибок, если изменение контракта не является осознанной частью задачи.

## 3. API и данные

Основные группы API включают:

- /api/health — health check.
- /api/rooms — номера и связанные с ними состояния.
- /api/products — продукты.
- /api/templates — шаблоны.
- /api/deadlines — сроки и связанные показатели.
- /api/checks — проверки, включая GIH-сценарии.
- /api/excises — акцизы.
- /api/lists — списки.
- /api/miniapp — операции Mini App.
- /api/vk-bot — внутренние операции бота.
- /api/events — поток live-событий Server-Sent Events (SSE).

Это обзор групп маршрутов, а не полный контракт API. Перед использованием конкретного endpoint изучи актуальный код в backend/src/routes/ и соответствующий frontend-вызов в frontend/config.js или другом клиенте.

В схеме встречаются, в частности, сущности Product, Room, FillTemplate, TemplateItem, RoomCustom, RoomProductStatus, ReplacementItem, Check, GihItem, Excise, ActiveList, ListRoom, DeadlineDailyStat, DeadlineTarget, ProductMonthCheck, MiniAppRoomTask, VkBotEvent и Setting. Перед изменением модели проверь фактическую схему в backend/prisma/schema.prisma; этот список не заменяет её.

### Правила работы с БД

1. Prisma-схема — исходный ориентир для структуры данных.
2. Backend при старте выполняет backend/src/init-db.js; в текущей реализации используется prisma db push и дополнительная SQL-логика, включая заполнение данных для GIH. Поэтому изменение схемы или инициализации может влиять на реальные данные и запуск production.
3. Не запускай миграции, db push, очистку таблиц, восстановление дампов или ручные SQL-изменения на production без предварительного анализа, согласованного плана и явного разрешения.
4. Не удаляй и не переименовывай поля/таблицы только ради упрощения кода: проверь историю, зависимости, API и клиентов.
5. Учитывай часовые пояса. Frontend передаёт X-Timezone-Offset; backend содержит общую логику timezone. Не вводи параллельную несовместимую логику дат.
6. Не помещай тестовые данные, реальные дампы или чувствительные данные отеля в Git.

## 4. Live-обновления

Приложение использует SSE через /api/events, чтобы изменения отображались без ручного обновления страницы.

- backend/src/lib/prisma.js отслеживает операции изменения данных и регистрирует события.
- backend/src/lib/live-events.js определяет публикацию событий и их домены.
- frontend/js/live-sync.js сопоставляет события с областями интерфейса и управляет реакцией клиента.
- Механизм учитывает активное редактирование, чтобы не прерывать работу пользователя неожиданной перезагрузкой данных.

При добавлении новой изменяющей операции проверь, проходит ли она через существующий механизм событий. Если появляется новая сущность или домен, согласованно обнови backend-маппинг и frontend-подписку. Не добавляй для одной функции независимый polling или локальную синхронизацию вместо общего механизма без обоснования.

Текущая история событий хранится в памяти процесса и ограничена последними 500 событиями; при перезапуске backend она не сохраняется. Публикация также локальна для одного процесса. Горизонтальное масштабирование backend потребует отдельного общего брокера/хранилища событий — нельзя считать текущий in-memory механизм межпроцессным.

## 5. Frontend, путь приложения и кеш

Production-приложение размещено под префиксом /minibar-os, а не в корне домена. Базовый путь определён в frontend/js/app-core.js; production API в frontend/config.js использует /minibar-os/api.

Не удаляй этот префикс и не меняй ссылки на корневые пути без проверки nginx и всех клиентских маршрутов. В frontend/config.js локальный режим сейчас указывает на http://localhost:3000/api, тогда как production Compose публикует backend на 127.0.0.1:3100; учитывай это несоответствие при настройке локального окружения, не меняя production-конфигурацию случайно.

Nginx может долго кешировать статические ресурсы с CSS/JS как immutable. Если меняешь файл, подключаемый из frontend/index.html, проверь версионирование URL ресурса (query string), чтобы браузеры не продолжали использовать старую версию.

Дизайн должен оставаться единым, профессиональным и удобным для работы за компьютером: понятная иерархия, читаемые состояния, предсказуемые действия. Не добавляй мелкие элементы, лишние пояснения, новые визуальные паттерны или перегруженные панели, если задача этого не требует. Сохраняй существующий стиль и проверяй интерфейс в реальном браузере.

## 6. Локальная разработка и Docker

В репозитории есть docker-compose.yml с сервисами db, backend, frontend, miniapp, vk-proxy и vk-bot. Backend зависит от health check PostgreSQL; остальные зависимости описаны в Compose.

Перед запуском изучи .env.example и актуальный Compose-файл, чтобы понять обязательные переменные. Не коммить .env или секреты. Backend-пакет предоставляет скрипты:

- npm start — инициализация БД, затем запуск API.
- npm run dev — инициализация БД, затем запуск с Node watch.

Так как запуск backend включает инициализацию схемы, **не направляй локальный процесс на production DATABASE_URL**. Локальная разработка должна использовать отдельную локальную/тестовую базу, если её настройка согласована и понятна.

Не считай приведённые выше сведения полной инструкцией по первому развёртыванию: перед командами сверяйся с текущими Dockerfile, Compose и переменными окружения.

## 7. Тесты и проверки

GitHub Actions workflow .github/workflows/desktop-smoke.yml выполняет сборку frontend-образа и desktop browser smoke-тесты в отдельном CI-окружении. Это полезная базовая проверка, но она не гарантирует корректность всех бизнес-сценариев, backend-операций, VK-интеграций или миграций БД.

Для frontend-изменений:
1. Проверь синтаксис изменённых JS/CSS/HTML-файлов.
2. Запусти доступные desktop smoke-тесты или дождись CI.
3. Проверь затронутые сценарии в браузере, включая ошибки API и обновление после изменения данных.
4. Убедись, что базовый путь /minibar-os и кеширование статических ресурсов не сломаны.

Для backend-изменений дополнительно:
1. Проверь маршруты, валидацию входных данных, статусы и формат ответов.
2. Проверь связанные операции Prisma и обработку ошибок.
3. Проверь влияние на SSE и все клиенты, использующие endpoint.
4. Для изменений схемы отдельно опиши совместимость и безопасный план обновления данных. Не проверяй такие изменения на production экспериментальным запуском.

## 8. Git и деплой

- main — основная ветка разработки.
- Перед изменениями проверь текущую ветку, незакоммиченные изменения и актуальность локальной копии.
- Не делай force-push, reset с потерей изменений, массовый cherry-pick или переписывание истории без явного согласования.
- Делай небольшие тематические коммиты с понятными сообщениями.
- Не включай в коммит секреты, дампы, локальные конфигурации и посторонние изменения.

### Как сейчас устроен production-деплой

Workflow в .github/workflows/desktop-smoke.yml после smoke-тестов может продвигать коммит из main в design/desktop-unification, а затем подключаться к VPS. Существующий серверный скрипт /usr/local/sbin/minibar-deploy использует эту deployment-ветку и пересобирает **только frontend**. В результате текущий путь деплоя не обновляет автоматически backend, БД, Mini App, VK proxy или bot.

Не предполагай, что push в main обновил все компоненты. Для изменений за пределами frontend сначала выясни и согласуй фактический безопасный путь выкладки; не запускай серверные команды наугад.

В GitHub Actions используются секреты VPS_HOST, VPS_SSH_PRIVATE_KEY и VPS_KNOWN_HOSTS. Никогда не выводи и не запрашивай значения этих секретов в логи или коммиты.

## 9. Preview и production-безопасность

**Preview-окружение отключено и не является частью текущего рабочего процесса.** Предыдущая попытка его использования привела к падению сервера, после чего было принято решение не использовать preview.

- Не создавай, не запускай, не восстанавливай и не перенастраивай preview-окружение на VPS без отдельного явного разрешения пользователя.
- Не запускай scripts/deploy-preview.sh, docker-compose.preview.yml или связанные с preview операции по собственной инициативе.
- Не делай эксперименты с Docker Compose, контейнерами, томами, дампами или базами на production VPS без заранее согласованного плана и ясного понимания воздействия.
- Не предполагай, что preview безопасен только потому, что у него отдельное имя проекта или том.
- Этот запрет не означает, что все preview-файлы обязательно удалены из репозитория или сервера; он означает, что их нельзя использовать без нового разрешения.

Безопасный обычный путь: изучить существующий код → внести минимальные изменения в GitHub → выполнить доступные CI-проверки → согласовать и выполнить предусмотренный путь деплоя. Не используй production как тестовый стенд.

## 10. VK-интеграции и секреты

VK Bot и VK API Proxy — серверные компоненты. Токены VK и внутренние токены backend должны оставаться на сервере и передаваться через защищённые переменные окружения. Не помещай их в frontend, Mini App, публичные конфиги, коммиты или скриншоты.

Backend поддерживает ограничения для разрешённых peer ID и внутреннюю авторизацию запросов бота. При изменениях VK-потоков проверь обе стороны: отправителя/клиент и серверный endpoint. Не ослабляй проверки доступа ради удобства тестирования.

Не отправляй реальные данные гостиницы, сотрудников или внутренние сообщения во внешние сервисы без явного разрешения.

## 11. Правила для ИИ-агентов

Перед тем как менять код:

1. **Определи фактическую задачу.** Не расширяй её на соседние функции без необходимости.
2. **Изучи текущую реализацию.** Найди маршрут UI, frontend-вызов, backend endpoint, сервис и модель данных, если они относятся к задаче.
3. **Проверь границы изменений.** Учитывай все клиенты общего API: desktop, Mini App и bot.
4. **Сохраняй совместимость.** Не меняй публичные API, структуру хранения, URL, названия событий и существующие пользовательские сценарии без обоснования.
5. **Не выдумывай результаты проверок.** Разделяй то, что проверено, то, что предполагается, и то, что ещё не проверено.
6. **Работай узко.** Не форматируй весь проект, не переписывай модуль целиком и не трогай не относящиеся к задаче файлы без причины.
7. **При риске потери данных остановись.** Сначала опиши риск и предложи безопасный план; не выполняй разрушительные операции без разрешения.
8. **Не считай наличие инструмента разрешением на его использование.** Доступ к серверу, Docker, GitHub или БД не означает разрешение на любые операции с ними.
9. **Не меняй другие проекты на сервере.** В частности, не трогай Tintink и его процессы/конфигурацию, если задача явно не относится к ним и пользователь не разрешил это.
10. **Отчитывайся конкретно.** Перечисли изменённые файлы, выполненные проверки, результаты и оставшиеся риски.

### Критерии готовности изменения

- Задача решена без побочных изменений.
- Связанные frontend/backend-контракты согласованы.
- Для изменённых сценариев проверены ошибки и граничные случаи.
- Live-обновления работают там, где они требуются.
- Не нарушены base path, стили и кеширование.
- Тесты выполнены либо явно указано, почему их выполнить не удалось.
- Production/БД не использовались для экспериментов.
- Коммит не содержит секретов или пользовательских данных.

## 12. Что проверять в первую очередь при новом подключении

1. Прочитать этот README и текущую задачу.
2. Проверить актуальную ветку и состояние Git.
3. Изучить нужные файлы и вызываемые ими зависимости.
4. Сверить поведение с реальной схемой и текущими endpoint, не полагаться только на документацию.
5. Уточнить, затрагивает ли задача production, БД, VK-секреты или другие клиенты.
6. Выполнить минимальные изменения и доступные проверки.
7. Только после этого предлагать или выполнять деплой в рамках согласованного процесса.
